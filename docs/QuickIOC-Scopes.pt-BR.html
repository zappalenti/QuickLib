Escopos e instâncias com dono (IOwned) no Quick.IOC

Um guia de como o container passou a controlar o tempo de vida "por escopo", escrito para quem já usa o Quick.IOC com AsTransient e AsSingleton. Primeiro o conceito e o uso. Depois, a história de uma requisição contada do começo ao fim: onde o escopo nasce, como ele chega a cada dependência, como um IOwned<T> cria um segundo escopo, quem mantém cada instância viva e como os escopos são liberados.

Os exemplos vêm de samples/delphi/QuickIOC/ScopedAndOwned, que tem a mesma aplicação em Horse (um escopo por requisição) e em VCL (um escopo para a aplicação inteira, que as telas usam por padrão), sem banco de dados.

1. O problema: transient e singleton não bastam

Até aqui o Quick.IOC oferecia dois tempos de vida:

Tempo de vidaO container entrega
AsTransientuma instância nova a cada resolução
AsSingletona mesma instância para a aplicação inteira

Pense numa API que grava um cliente e uma linha de auditoria. O serviço usa dois repositórios, e os dois precisam trabalhar na mesma conexão e na mesma transação: se a gravação do cliente for desfeita, a auditoria também deve ser. A conexão com a transação é a "unidade de trabalho" (IUnitOfWork).

  • Com AsTransient, cada repositório recebe a sua própria unidade de trabalho: são duas conexões, e a transação de uma não vale para a outra.
  • Com AsSingleton, todas as requisições compartilham a mesma unidade de trabalho: a transação de uma requisição se mistura com a de outra, e uma conexão passa a ser usada por várias threads.

O que se quer é um meio-termo: uma instância por requisição. Dentro da requisição, todos recebem a mesma unidade de trabalho; outra requisição recebe outra. É isso que AsScoped faz: o "escopo" é a fronteira (uma requisição, uma tela, uma tarefa) dentro da qual a instância é compartilhada.

Antes desta mudança, AsScoped já existia na API, mas o container não tinha um objeto de escopo: um registro AsScoped era resolvido como transient. Agora o escopo é um objeto, TIocScope.

2. Usando escopos

O registro diz o tempo de vida de cada serviço. É o que o exemplo faz, em Common/ScopedAndOwned.Registration.pas:

  // ---- SINGLETON: one instance for the whole application ----------------------------------
  aContainer.RegisterInstance<IActivityLog>(aLog).AsSingleton;
  aContainer.RegisterType<IFakeDatabase, TFakeDatabase>.AsSingleton;

  // ---- SCOPED: one instance per scope ------------------------------------------------------
  // The scope is the request's (Horse), the application's or a screen's own (VCL), or an IOwned's
  aContainer.RegisterType<IUnitOfWork, TFakeUnitOfWork>.AsScoped;
  aContainer.RegisterType<ICustomerRepository, TCustomerRepository>.AsScoped;
  // also registers IOwned<IAuditRepository> (AutoRegisterOwned, True by default)
  aContainer.RegisterType<IAuditRepository, TAuditRepository>.AsScoped;

  // ---- TRANSIENT: a new instance on every resolution ---------------------------------------
  aContainer.RegisterType<IOwnedAuditService, TOwnedAuditService>.AsTransient;
  aContainer.RegisterType<ISameTransactionAuditService, TSameTransactionAuditService>.AsTransient;

Quem define a fronteira é quem cria e libera o escopo. No Horse, um middleware abre um escopo no início de cada requisição e o libera no fim (Horse/ScopedAndOwned.ScopePerRequest.pas):

procedure ScopePerRequest(Req: THorseRequest; Res: THorseResponse; Next: TProc);
var
  scope: TIocScope;
  session: TScopeSession;
begin
  scope := GlobalContainer.CreateScope;
  try
    session := TScopeSession.Create; // owned by Req.Sessions; the scope is owned by this middleware
    session.fScope := scope;
    Req.Sessions.SetSession(TScopeSession, session);
    try
      Next();
    finally
      session.fScope := nil;
    end;
  finally
    // Free releases every instance of the scope, and raises again the first exception raised by
    // their destructors. The response is already built at this point: report it, do not raise it
    try
      scope.Free;
    except
      on E: Exception do
        Writeln(ErrOutput, 'Error releasing the request scope: ', E.ClassName, ': ', E.Message);
    end;
  end;
end;

E a rota resolve a partir do escopo da requisição (Horse/ScopedAndOwned.Routes.pas):

  service := RequestScope(Req).Resolve<IOwnedAuditService>;
  Save(service, Req, Res);
  // releasing the service releases its IOwned, and with it the IOwned's scope
  service := nil;

No VCL: um escopo para a aplicação inteira

No exemplo VCL, o primeiro escopo pertence à aplicação: ele nasce no .dpr, antes do formulário principal, e é liberado no fim, depois de todos os formulários. Por padrão, toda tela usa esse escopo e, portanto, compartilha a mesma unidade de trabalho, que faz o papel da conexão aberta da aplicação (VCL/ScopedAndOwnedVcl.dpr):

  // scope A: created with the application, before any form; every form uses it by default
  CreateApplicationScope;
  Application.CreateForm(TMainForm, MainForm);

O escopo fica num componente de Application, criado antes de qualquer formulário (VCL/ScopedAndOwned.ApplicationScope.pas):

type
  //owned by Application and created before any form: Application frees its components in reverse
  //order of creation, so the scope is freed after every form, when no form uses it anymore
  TApplicationScopeHolder = class(TComponent)

O formulário principal, como qualquer outro, resolve a partir dele, e isso abre a conexão da aplicação logo na partida (VCL/ScopedAndOwned.MainForm.pas):

  fConnection := ApplicationScope.Resolve<IUnitOfWork>;

Uma tela tem dois construtores: o padrão usa o escopo da aplicação (ou o escopo que receber), e o outro cria um escopo só dela, desligado do escopo da aplicação, liberado quando a tela fecha (VCL/ScopedAndOwned.ScreenForm.pas):

constructor TScreenForm.CreateFor(aOwner: TComponent; aKind: TAuditKind; aScope: TIocScope);
begin
  if aScope = nil then aScope := ApplicationScope;
  fScope := aScope;
  inherited Create(aOwner);
  Setup(aKind);
end;

constructor TScreenForm.CreateWithOwnScope(aOwner: TComponent; aKind: TAuditKind);
begin
  fScope := GlobalContainer.CreateScope;
  fOwnsScope := True;
  inherited Create(aOwner);
  Setup(aKind);
end;
  // released first: the service, and for akOwned its IOwned with the IOwned's scope
  fService := nil;
  // only a scope of its own is freed here: the application's scope lives as long as the application
  if fOwnsScope then fScope.Free;

As três maneiras de uma parte do sistema ganhar uma unidade de trabalho própria, saindo da conexão da aplicação:

Quem decideComoQuando o escopo novo é liberado

Resumo do uso: CreateScope abre, scope.Resolve<T> resolve dentro dele, scope.Free libera tudo o que foi criado nele. Quem chama CreateScope é dono do escopo e precisa liberá-lo, e sempre antes do container.

3. A história de uma requisição

Para entender o que acontece por dentro, vamos acompanhar uma única requisição do exemplo Horse, POST /owned?name=Ann&rollback=true, do começo ao fim. No VCL a história é a mesma; só muda o primeiro escopo: em vez de um por requisição, há um para a aplicação inteira, que as telas usam por padrão.

O serviço dessa rota é o TOwnedAuditService. Ele grava o cliente e a auditoria, e pede o repositório de auditoria como IOwned<IAuditRepository> (o porquê está no passo 4):

constructor TOwnedAuditService.Create(aUnitOfWork: IUnitOfWork; aCustomers: ICustomerRepository;
  aAudit: IOwned<IAuditRepository>);
begin
  inherited Create;
  fUnitOfWork := aUnitOfWork; // from the scope that resolved the service
  fCustomers := aCustomers;   // from the same scope: the same unit of work
  fAudit := aAudit;           // a scope of its own: another unit of work
end;

Nessa requisição aparecem dois escopos. Vamos chamá-los assim no resto do guia:

  • Escopo A, o da requisição: o middleware cria quando a requisição chega e libera quando ela termina. No VCL do exemplo, é o escopo da aplicação, que as telas usam por padrão (ou o escopo próprio de uma tela aberta com CreateWithOwnScope). É o escopo inicial, de onde a resolução parte.
  • Escopo B, o do IOwned: nasce durante a resolução do serviço, porque ele pede um IOwned, e é liberado quando o serviço solta esse IOwned.

4. Passo 1: o Escopo A nasce

O middleware chama CreateScope. Criar um escopo é barato: só o objeto é criado, e nada é construído até a primeira resolução.

function TIocContainer.CreateScope: TIocScope;
begin
  Result := TIocScope.Create(fResolver);
end;

O escopo é um objeto simples: o resolvedor que ele usa, duas tabelas "registro → instância" e duas listas com a ordem de criação. Declaração em Quick.IOC.pas:

  TIocScope = class
  private
    fResolver : TIocResolver;
    fReleasing : Boolean;
    fInterfaces : TDictionary<TIocRegistration, IInterface>;
    fObjects : TDictionary<TIocRegistration, TObject>;
    fCreated : TList<IInterface>;
    fCreatedObjects : TList<TObject>;
    procedure CheckAlive;
    function GetOrCreate(aReg : TIocRegistration; aServiceType : PTypeInfo) : TValue;
  public
    constructor Create(aResolver : TIocResolver);
    destructor Destroy; override;
    function Resolve<T>(const aName : string = ''): T; overload;
    function Resolve(aServiceType: PTypeInfo; const aName : string = ''): TValue; overload;
  end;
CampoPara que serve
fInterfacesa instância de cada registro (de interface) já criada neste escopo: é a busca "já existe?"
fObjectso mesmo para registros de classe (RegisterInstance<TClasse>), que não são interfaces
fCreated, fCreatedObjectsa ordem em que as instâncias foram criadas, para liberar na ordem inversa
fReleasingligado no início do Free: a partir daí o escopo recusa resolver

A chave das tabelas é o registro (TIocRegistration), não o tipo. Cada RegisterType cria um registro; o escopo guarda no máximo uma instância por registro.

Mais adiante, no passo 4, o Escopo B será criado pelo mesmo CreateScope. Os dois são objetos TIocScope idênticos: o que diferencia um do outro é só quem os criou e quem os segura.

5. Passo 2: a resolução leva o escopo junto

A rota pede o serviço ao Escopo A: RequestScope(Req).Resolve<IOwnedAuditService>. O serviço pede IUnitOfWork no construtor, e o TCustomerRepository também. Como o container sabe que essas unidades de trabalho devem vir do Escopo A?

Não existe um "escopo atual" guardado em algum lugar, nem variável global nem pilha nem contador. O escopo viaja como parâmetro, aScope, por toda a cadeia de resolução. Cada etapa recebe aScope e o repassa à seguinte.

aScope é sempre o escopo de onde a resolução partiu:

Quem pediuaScope
a rota, com RequestScope(Req).Resolve; no VCL, a tela, com fScope.Resolveo Escopo A (no VCL, o da aplicação ou o próprio da tela)
o delegate do IOwned, durante o passo 4o Escopo B
alguém com GlobalContainer.Resolve, sem escoponil

No passo 2 da nossa história, aScope é o Escopo A:

O ponto de entrada é o Resolve do escopo, que passa a si mesmo (Self) ao resolvedor: é aqui que o Escopo A entra na cadeia.

function TIocScope.Resolve(aServiceType: PTypeInfo; const aName: string): TValue;
begin
  CheckAlive;
  Result := fResolver.Resolve(aServiceType,aName,Self);
end;

O Resolve "antigo", sem escopo, continua existindo e passa nil: é o que o container raiz usa.

function TIocResolver.Resolve(aServiceType: PTypeInfo; const aName : string = ''): TValue;
begin
  Result := Resolve(aServiceType,aName,nil);
end;

Na construção por RTTI, cada parâmetro do construtor é resolvido com o mesmo aScope (trecho do TryInvoke, dentro de TIocResolver.CreateInstance):

        try lVal := Resolve(lParam.ParamType.Handle, lName, aScope);
        except on EIocResolverError do Exit; // required dep not found
        end;

É assim que a dependência da dependência, em qualquer profundidade, cai no mesmo escopo: cada chamada recursiva recebe o mesmo aScope. Não há nada a "descobrir": o escopo é um argumento.

6. Passo 3: cada dependência, conforme o tempo de vida

Para cada dependência, o TIocResolver.Resolve encontra o registro (o último registrado para o tipo e o nome) e decide pelo tempo de vida dele. No passo 3, aScope é o Escopo A:

Na nossa requisição:

  • IOwnedAuditService é transient: é construído na hora, com o mesmo aScope (o Escopo A), e não fica guardado no escopo.
  • IUnitOfWork é scoped e aScope é o Escopo A: o A cria a UnitOfWork 1 e a guarda.
  • ICustomerRepository é scoped: o A cria o repositório. O construtor dele pede IUnitOfWork de novo, e o A devolve a mesma UnitOfWork 1, que já está guardada.

O trecho novo do Resolve é o desvio do scoped, logo depois de achar o registro:

  //scoped: one instance per scope, created and released by the scope
  if reg.IsScoped then
  begin
    if aScope <> nil then Exit(aScope.GetOrCreate(reg,aServiceType));
    if fValidateScopes then
      raise EIocScopeError.CreateFmt('Scoped service "%s" resolved outside a scope. Resolve it from a TIocScope ' +
        '(TIocContainer.CreateScope), not from the root container nor as a dependency of a singleton; or set ' +
        'ValidateScopes := False to keep the previous behaviour (resolved as transient).',[aServiceType.Name]);
    //ValidateScopes = False: previous behaviour, built below as a transient
  end;

E, no caminho do singleton, a linha que "esquece" o escopo antes de construir (o motivo está na seção 12):

    //dependencies of a singleton are resolved with no scope: a scoped one would be captured for
    //the whole application lifetime, so it raises EIocScopeError instead
    aScope := nil;
  end;
  //instance not created yet or needs to be created (transient)
  Result := BuildValue(reg,aServiceType,aScope);

GetOrCreate: "a mesma instância dentro do escopo"

O escopo procura o registro na sua tabela. Se não achar, manda o resolvedor construir passando a si mesmo como escopo (para as dependências) e guarda o resultado na tabela e na lista de criação:

function TIocScope.GetOrCreate(aReg: TIocRegistration; aServiceType: PTypeInfo): TValue;
var
  cached : IInterface;
  intf : IInterface;
  obj : TObject;
begin
  //the single place where the scope creates and keeps instances: reached from Resolve, but also
  //from dependency chains and IOwned
  CheckAlive;
  if aReg is TIocRegistrationInterface then
  begin
    if not fInterfaces.TryGetValue(aReg,cached) then
    begin
      //dependencies are resolved within this same scope
      cached := fResolver.BuildValue(aReg,aServiceType,Self).AsInterface;
      fInterfaces.Add(aReg,cached);
      fCreated.Add(cached);
    end;
    if cached.QueryInterface(GetTypeData(aServiceType).Guid,intf) <> 0 then
      raise EIocResolverError.CreateFmt('Implementation for "%s" not registered!',[aServiceType.Name]);
    TValue.Make(@intf,aServiceType,Result);
  end

BuildValue é a parte do Resolve antigo que constrói a instância, separada para que o escopo a use também. Ela nunca guarda nada: quem guarda é o chamador (o escopo, para scoped; o registro, para singleton). Repare na penúltima linha deste trecho: o delegate (DelegateTo) é chamado sem o escopo; só a construção por construtor o recebe. Esse detalhe é a chave do passo 4.

function TIocResolver.BuildValue(aReg: TIocRegistration; aServiceType: PTypeInfo; aScope: TIocScope): TValue;
var
  intf : IInterface;
  newInst : IInterface;
begin
  //builds a new instance, never caches: shared by Resolve and by the scopes
  if aReg is TIocRegistrationInterface then
  begin
    //if instance already set (RegisterInstance<TInterface>(obj)), use it directly
    newInst := TIocRegistrationInterface(aReg).Instance;
    if newInst = nil then
    begin
      //otherwise, create new instance from &Implementation
      if aReg.&Implementation = nil then raise EIocResolverError.CreateFmt('Implemention for "%s" not defined!',[aServiceType.Name]);
      {$IFDEF DEBUG_IOC}
      TDebugger.Trace(Self,'Building dependency: %s',[aReg.fIntfInfo.Name]);
      {$ENDIF}
      if Assigned(aReg.ActivatorDelegate) then newInst := aReg.ActivatorDelegate().AsInterface
        else newInst := CreateInstance(aReg.&Implementation,aScope).AsInterface;

7. Passo 4: o serviço pede um IOwned

O terceiro parâmetro do construtor do serviço é IOwned<IAuditRepository>. Por que não simplesmente IAuditRepository?

Dentro do Escopo A, todos recebem a mesma UnitOfWork 1. Às vezes uma parte do grafo precisa justamente do contrário: a sua própria. No exemplo, a auditoria deve ficar registrada mesmo que a gravação do cliente seja desfeita (é a prova de que alguém tentou). Se o repositório de auditoria usasse a UnitOfWork 1, o rollback levaria a auditoria junto. Ele precisa de outra unidade de trabalho, fora da transação.

IOwned<T> (inspirado no Owned<T> do Autofac) resolve isso: o construtor pede IOwned<T> em vez de T, e o container resolve T num escopo novo, só dele, o Escopo B, que vive enquanto o IOwned<T> for referenciado.

Os dois serviços do exemplo usam os mesmos registros; só o construtor muda. O TSameTransactionAuditService, da rota /same-transaction, pede o repositório direto:

constructor TSameTransactionAuditService.Create(aUnitOfWork: IUnitOfWork; aCustomers: ICustomerRepository;
  aAudit: IAuditRepository);
begin
  inherited Create;
  fUnitOfWork := aUnitOfWork; // the three references point to the same unit of work
  fCustomers := aCustomers;
  fAudit := aAudit;
end;

O resultado, nas duas rotas:

Com rollback=true, a UnitOfWork 1 desfaz o cliente, e a UnitOfWork 2 já gravou a auditoria. Com o TSameTransactionAuditService, tudo está na UnitOfWork 1, e o rollback desfaz os dois.

O serviço guarda o IOwned, não só o Value. É a referência ao IOwned que mantém o Escopo B vivo (seções 10 e 11):

function TOwnedAuditService.Save(const aName: string; aRollback: Boolean): TSaveResult;
begin
  Result := SaveCustomer('OwnedAuditService', fUnitOfWork, fCustomers, fAudit.Value, aName, aRollback);
end;

8. Por dentro do passo 4: como o IOwned cria o Escopo B

O registro: feito no RegisterType

IOwned<IAuditRepository> é um tipo genérico, e o Delphi não consegue montar um tipo genérico novo em tempo de execução a partir de IAuditRepository. Por isso o IOwned<I> é registrado no momento em que I é registrado, quando o compilador ainda conhece o tipo:

function TIocContainer.RegisterType<TInterface, TImplementation>(const aName: string): TIocRegistration<TImplementation>;
begin
  Result := fRegistrator.RegisterType<TInterface, TImplementation>(aName);
  //IOwned<TInterface> must be registered here: generic types cannot be instantiated at runtime
  if fAutoRegisterOwned then RegisterOwned<TInterface>(aName);
end;

RegisterOwned<I> confere que I está registrado e, se o IOwned<I> ainda não existir para essa chave, chama AddOwned<I>. É um IOwned por chave (tipo e nome): ele resolve o que Resolve<I> devolve, então acompanha também um registro de I feito depois.

procedure TIocContainer.RegisterOwned<TInterface>(const aName : string);
var
  named : string;
begin
  if not fRegistrator.IsRegistered<TInterface>(aName) then
  begin
    if aName.IsEmpty then named := ''
      else named := ' with the name "' + aName + '"';
    raise EIocRegisterError.CreateFmt('RegisterOwned<%s>: %s is not registered%s; register it first',
      [GetTypeName(TypeInfo(TInterface)),GetTypeName(TypeInfo(TInterface)),named]);
  end;
  //one IOwned per key: it resolves what Resolve<TInterface> returns, so it also follows a
  //registration added later
  if not fRegistrator.IsRegistered<IOwned<TInterface>>(aName) then AddOwned<TInterface>(aName);
end;

O AddOwned<T> é o coração do mecanismo. Ele registra IOwned<T> como transient (cada consumidor ganha o seu) e com um delegate que faz todo o trabalho:

procedure TIocContainer.AddOwned<T>(const aName : string);
var
  container : TIocContainer;
  regName : string;
begin
  container := Self;
  regName := aName;
  //transient: every consumer gets its own scope. Registered through the non-generic
  //RegisterType so it does not register an IOwned of IOwned<T>
  fRegistrator.RegisterType(TypeInfo(IOwned<T>),TOwned<T>,aName).ActivatorDelegate :=
    function : TValue
    var
      scope : TIocScope;
      owned : IOwned<T>;
    begin
      //independent scope: it does not see the consumer's scoped instances, only singletons
      scope := container.CreateScope;
      try
        owned := TOwned<T>.Create(scope,scope.Resolve<T>(regName));
      except
        //the resolution failure is what the caller must see: an exception raised while releasing
        //what was already created in the scope is dropped instead of hiding it
        try
          scope.Free;
        except
        end;
        raise;
      end;
      Result := TValue.From<IOwned<T>>(owned);
    end;
end;

Lendo o delegate linha a linha, na nossa requisição:

  1. container.CreateScope: é aqui que o Escopo B nasce, igual a qualquer outro escopo.
  2. scope.Resolve<T>(regName): resolve IAuditRepository no Escopo B. Daqui para baixo, o aScope que viaja pela cadeia (seção 5) é o B: o AuditRepository pede IUnitOfWork, e o B cria a UnitOfWork 2.
  3. TOwned<T>.Create(scope, ...): embrulha o valor e entrega o Escopo B ao TOwned, que passa a ser o dono dele.
  4. Se a resolução falhar, o Escopo B é liberado ali mesmo, e o erro original é o que sobe.

Quem não quiser o registro automático desliga AutoRegisterOwned e chama RegisterOwned<I> só onde precisa. RegisterOwned<I> também cobre o que RegisterType<I,T> não cobre: o RegisterType não genérico e o RegisterInstance.

A resolução: o resolvedor não "detecta" nada

Como o resolvedor percebe que o parâmetro IOwned<IAuditRepository> precisa de um escopo novo? Ele não percebe. Para o resolvedor, IOwned<IAuditRepository> é só mais um registro transient, cujo delegate, por acaso, cria um escopo:

O detalhe que faz tudo funcionar está no BuildValue (seção 6): o delegate é chamado como aReg.ActivatorDelegate(), sem o Escopo A. O delegate não tem como enxergar o escopo do consumidor e, por isso, cria o seu. É por construção que o Escopo B é independente do A.

O único lugar em que o resolvedor reconhece um IOwned explicitamente é uma verificação de configuração, no TryInvoke: se o construtor pede um IOwned<I> que não foi registrado, é um erro de registro, e não um motivo para tentar outro construtor:

        //IOwned<I> is asked for on purpose, for a scope of its own: without its registration this
        //is a configuration error, never a reason to try another constructor
        if IsOwnedType(lParam.ParamType.Handle) and
          not fRegistrator.Dependencies.ContainsKey(fRegistrator.GetKey(lParam.ParamType.Handle,lName)) then
          raise EIocRegisterError.CreateFmt('%s.%s asks for %s, which is not registered: call RegisterOwned or ' +
            'enable AutoRegisterOwned',[aCtor.Parent.Name,aCtor.Name,lParam.ParamType.Name]);

E IsOwnedType reconhece qualquer IOwned<...> pelo GUID, que é o mesmo para todas as instâncias de uma interface genérica:

function IsOwnedType(aType : PTypeInfo) : Boolean;
begin
  //every IOwned<T> has the GUID of the generic declaration: what tells them apart from other
  //interfaces without knowing T
  Result := (aType <> nil) and (aType.Kind = tkInterface) and
    IsEqualGUID(GetTypeData(aType).Guid,GetTypeData(TypeInfo(IOwned<IInterface>)).Guid);
end;

9. Escopo A e Escopo B: aninhados, mas sem hierarquia

É comum imaginar os escopos como uma árvore: o Escopo B seria "filho" do Escopo A, o container saberia em que nível está, e um escopo filho enxergaria as instâncias do pai. Não é assim.

O que não existe:

  • um campo "escopo pai" no TIocScope;
  • um número de nível ou de profundidade;
  • a herança de instâncias: o Escopo B não vê a UnitOfWork 1 do A (por isso ele cria a UnitOfWork 2, que é justamente o objetivo).

O que existe é um encadeamento de referências entre objetos. O serviço (resolvido no Escopo A) segura o IOwned; o TOwned segura o Escopo B; o Escopo B segura as instâncias dele. Se o AuditRepository, dentro do Escopo B, pedisse outro IOwned<U>, nasceria um Escopo C, seguro por ele. A "profundidade" aparece sozinha, pelo grafo de objetos:

Para o container, os três escopos são irmãos: cada um foi criado por CreateScope e só conhece o resolvedor. O que eles compartilham são os singletons, que pertencem aos registros e não a um escopo. O "aninhamento" está em quem segura quem, e é isso que define quando cada escopo é liberado: o assunto das duas próximas seções.

10. Quem mantém cada instância viva: o "incrementa e decrementa"

A história chegou ao meio: o serviço gravou (passo 5) e agora tudo precisa ser liberado. Antes de ver os passos 6 e 7, a pergunta é: o que mantém cada instância viva, e o que a faz morrer? O container conta quantos escopos existem, ou quantas vezes uma instância foi entregue?

O container não tem contador, nem de instâncias nem de escopos nem de níveis. Quem conta é o Delphi: toda instância entregue como interface tem contagem de referências. Cada variável, campo ou lista que recebe a interface soma 1 (_AddRef); cada uma que a solta subtrai 1 (_Release); quando chega a zero, o destrutor roda. O que o container faz é segurar referências e soltá-las na hora certa.

Essa mesma contagem governa os dois escopos da história, de dois jeitos diferentes:

O que a contagem decide
Escopo Aquando cada instância dele morre. O escopo segura duas referências a cada instância (na tabela e na lista); os objetos que receberam a instância seguram outras. Ela só morre quando todas forem soltas.
Escopo Bquando o escopo inteiro é liberado. O serviço segura o IOwned; quando a contagem do IOwned chega a zero, o TOwned é destruído e libera o Escopo B.

No Escopo A: a contagem da UnitOfWork 1

No Escopo B: a contagem do IOwned

No passo 4, o delegate entregou ao serviço um IOwned (o objeto TOwned), e o serviço o guardou no campo fAudit: é a única referência a ele. No passo 6, a rota solta o serviço; o serviço, ao ser destruído, solta o fAudit; a contagem do IOwned chega a zero, e o TOwned é destruído. O destrutor dele libera o Escopo B. A seção 11 mostra esse destrutor.

Três consequências práticas:

  • Um escopo não destrói ninguém à força quando se trata de interfaces: ele solta as referências dele. Se alguém de fora ainda segurar a instância, ela sobrevive ao escopo, fora do controle dele. Por isso as rotas e telas do exemplo soltam o serviço (service := nil, fService := nil) antes do scope.Free.
  • Registros de classe (RegisterInstance<TClasse>, sem interface) não têm contagem: o escopo é dono deles e os destrói com Free na liberação. Quem ainda tiver um ponteiro para eles fica com memória liberada.
  • O Escopo B vive enquanto alguém segurar o IOwned, nem mais nem menos. Se o serviço fosse um singleton, o Escopo B viveria a aplicação inteira; se fosse scoped no A, o B seria liberado durante a liberação do A. No VCL do exemplo, a tela segura o serviço: o escopo do IOwned vive enquanto a tela estiver aberta, mesmo que ela use o escopo da aplicação.

11. Passos 6 e 7: a liberação dos escopos

Na nossa requisição, os escopos saem nesta ordem: primeiro o B (passo 6, quando a rota solta o serviço), depois o A (passo 7, quando o middleware chama scope.Free).

Passo 6: o TOwned libera o Escopo B

O TOwned<T> é o dono do Escopo B. Ele guarda o escopo e o valor:

  TOwned<T> = class(TInterfacedObject,IOwned<T>)
  private
    fScope : TIocScope;
    fValue : T;
  public
    constructor Create(aScope : TIocScope; const aValue : T);
    destructor Destroy; override;
    function Value : T;
  end;

Como é um TInterfacedObject, ele morre quando a última referência ao IOwned<T> é solta (seção 10). O destrutor solta o valor antes de liberar o escopo (o valor pode apontar para instâncias do escopo) e libera o escopo mesmo que o destrutor do valor lance:

destructor TOwned<T>.Destroy;
begin
  //release the value before its scope: it may hold references to the scope's instances
  try
    fValue := Default(T);
  except
    //the scope is released anyway, so its instances do not leak; the value's exception is the
    //one raised (one raised while releasing the scope is dropped)
    try
      fScope.Free;
    except
    end;
    raise;
  end;
  fScope.Free;
  inherited;
end;

O fScope.Free é a liberação de um escopo como qualquer outro, descrita logo abaixo. A cadeia completa dos passos 6 e 7:

Passo 7, e o fim de qualquer escopo: TIocScope.Destroy

O destrutor do escopo é o mesmo para o A e para o B. Ele faz quatro coisas, nesta ordem:

destructor TIocScope.Destroy;
var
  i : Integer;
  firstError : TObject;
begin
  //from now on nothing is resolved from this scope, not even by the destructors of its instances
  fReleasing := True;
  //a destructor that raises must not stop the release of the others: the first exception is
  //kept and raised again once everything is released
  firstError := nil;
  //release in reverse order of creation: dependents go before their dependencies
  fInterfaces.Clear;
  for i := fCreated.Count - 1 downto 0 do
  begin
    try
      fCreated[i] := nil;
    except
      if firstError = nil then firstError := TObject(AcquireExceptionObject);
    end;
  end;
  fCreated.Free;
  fInterfaces.Free;
  //class (non-interface) scoped instances are owned by the scope
  fObjects.Clear;
  for i := fCreatedObjects.Count - 1 downto 0 do
  begin
    try
      fCreatedObjects[i].Free;
    except
      if firstError = nil then firstError := TObject(AcquireExceptionObject);
    end;
  end;
  fCreatedObjects.Free;
  fObjects.Free;
  inherited;
  if firstError <> nil then raise firstError;
end;

1. Fecha a porta (fReleasing := True). Um destrutor de uma instância do escopo pode tentar resolver algo do próprio escopo. Sem a porta fechada, o escopo criaria uma instância nova enquanto suas listas estão sendo destruídas. Com ela, CheckAlive responde com EIocScopeError:

procedure TIocScope.CheckAlive;
begin
  if fReleasing then
    raise EIocScopeError.Create('The scope is being freed: nothing can be resolved from it anymore ' +
      '(e.g. from the destructor of one of its instances).');
end;

2. Ordem inversa da criação. Com injeção por construtor, a dependência é sempre criada antes de quem depende dela: para construir o CustomerRepository, o container primeiro resolve a UnitOfWork. Na lista fCreated do Escopo A, portanto, a UnitOfWork 1 vem antes. Percorrendo a lista de trás para frente, quem depende sai primeiro, e a dependência sai por último, quando ninguém mais do escopo precisa dela.

3. Um destrutor que lança não interrompe os outros. Cada liberação está num try/except; a primeira exceção é guardada (AcquireExceptionObject, que a tira do mecanismo de exceções para que não seja destruída), e as demais instâncias continuam sendo liberadas. Sem isso, um destrutor com defeito deixaria todas as instâncias seguintes vivas para sempre.

4. Relança no fim. Depois de liberar tudo e destruir as próprias listas, o escopo relança a primeira exceção: o erro não some, e as demais instâncias são liberadas. Perde-se só a memória do próprio escopo e a da instância cujo destrutor lançou, porque um destrutor que lança pula a liberação da memória do objeto (FreeInstance). Por isso o middleware do exemplo captura a exceção do scope.Free e a registra: nesse ponto a resposta já foi montada.

12. E quando não há escopo? ValidateScopes e a dependência capturada

A história acabou, mas falta um caso: o que acontece se um serviço scoped for pedido fora de um escopo, com aScope = nil?

  • Pelo container raiz (GlobalContainer.Resolve<IUnitOfWork>): não há escopo para guardar a instância.
  • Como dependência de um singleton: o singleton vive a aplicação inteira; se recebesse a UnitOfWork de uma requisição, ficaria com ela depois que a requisição terminasse.

O segundo caso é o mais perigoso, e tem nome: dependência capturada.

Por isso o caminho do singleton zera o escopo (aScope := nil, na seção 6) antes de construir: qualquer dependência scoped do singleton cai no caso "fora de escopo". E, com ValidateScopes = True (o padrão), fora de escopo é erro: EIocScopeError, com uma mensagem que diz o que fazer.

ValidateScopes := False devolve o comportamento anterior (scoped fora de escopo construído como transient), para quem já registrava AsScoped e resolvia pelo container raiz:

    /// <summary>True (default): resolving a scoped service outside a scope (from the root
    /// container or as a dependency of a singleton) raises EIocScopeError.
    /// False: previous behaviour, a scoped service outside a scope is built as transient.</summary>
    property ValidateScopes : Boolean read fValidateScopes write fValidateScopes;

Um IOwned resolvido pelo container raiz, ou por um singleton, não cai nesse erro: ele cria o próprio escopo, e as dependências scoped dele nascem lá.

Por que EIocScopeError não descende de EIocResolverError

A construção por construtor engole EIocResolverError de um parâmetro para tentar o próximo construtor (o except on EIocResolverError do Exit da seção 5). Se o erro de escopo fosse um EIocResolverError, o container desistiria do construtor certo e usaria outro, por exemplo o TObject.Create herdado, e o objeto nasceria com a dependência nil, sem erro nenhum. Por isso EIocScopeError descende de Exception diretamente e sempre chega a quem chamou.

13. Regras práticas e armadilhas

Libere o escopo antes do container, quando puder. O escopo resolve pelo resolvedor do container: resolver de um escopo depois de o container ser liberado lê memória liberada. Liberar o escopo não usa o container.

Não resolva nada em destrutores. Um destrutor de uma instância do escopo que resolve do próprio escopo recebe EIocScopeError (a porta já está fechada, seção 11).

Solte o que veio do escopo antes de liberá-lo. O escopo só solta as referências dele (seção 10). Uma variável que ainda segura a instância a mantém viva depois do escopo, e então ela é destruída fora de hora, quando a variável for solta.

Cuidado com temporários implícitos. Uma chamada encadeada como scope.Resolve<ILogger>.Log('x') cria uma referência escondida que o compilador só solta no fim da rotina, depois de um scope.Free feito no meio dela. Use uma variável explícita e atribua nil antes do Free, como fazem as rotas do exemplo.

Guarde o IOwned, não só o Value. Soltar o IOwned libera o escopo dele. Instâncias de interface seguras pelo Value continuam vivas, mas fora do controle de qualquer escopo; instâncias de classe do escopo são destruídas, e quem ainda as usar lê memória liberada.

Um escopo é de uma thread por vez. As tabelas do escopo não têm trava. No Horse, cada requisição tem o seu escopo, e é isso que torna o uso seguro.

Crie os singletons antes de atender em várias threads. A criação de um singleton não tem trava: se duas threads pedirem o mesmo singleton pela primeira vez ao mesmo tempo, as duas podem construí-lo. Por isso o exemplo Horse chama GlobalContainer.Build antes do THorse.Listen: o Build cria os singletons enquanto a aplicação ainda tem uma thread só.

Transient não pertence ao escopo. Um transient resolvido dentro de um escopo recebe as dependências scoped do escopo, mas é mantido por quem o resolveu, e não é liberado pelo escopo.

Scoped dentro de singleton é erro, de propósito. Se um singleton precisa de algo por requisição, ele pede um IOwned<T> (e controla quando soltá-lo) ou recebe o valor por parâmetro em cada chamada.

Um IOwned que não foi registrado é erro de configuração. Pedir IOwned<I> sem registro lança EIocRegisterError ao construir o consumidor, com o nome do construtor e o que fazer.
